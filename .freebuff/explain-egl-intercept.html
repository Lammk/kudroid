How KuDroid hijacks eglGetDisplay on iOS

A visual walkthrough of the latest GPU-shim commit: making Android games get our EGL display function — no matter which of the two lookup APIs they use to ask for it.

01Context: where this code lives

KuDroid loads an Android app's native .so (an ARM64 ELF built against bionic) with a custom loader, then answers every bionic entry point the binary touches with a shim that translates Android API calls into iOS-native calls. The GPU shim is one table of such translations.

This commit is one cell in that middle layer

The shim's job for EGL display functions: take the Android game's EGL calls and make them valid for ANGLE-on-Metal. The interception must happen at the moment the game resolves the function pointer — that's the part this commit hardens.

02The problem: two roads to the same function

Android games resolve EGL entry points through two different APIs. KuDroid must intercept both, or the game gets ANGLE's raw function and the shim's translation logic never runs.

🛣️ Road A — dlsym

The game calls dlsym(libEGL_handle, "eglGetDisplay"). KuDroid intercepts this as bionic_dlsym (SyscallShim).

Before the fix: bionic_dlopen("libEGL.so") returns a real ANGLE handle, so the "look in the real handle" step usually succeeded and returned ANGLE's real eglGetDisplay — the shim's version was only found later, as a fallback that was rarely reached.

🛣️ Road B — eglGetProcAddress

The game calls eglGetProcAddress("eglGetDisplay"). KuDroid intercepts this as bionic_eglGetProcAddress (GraphicsShim).

Before the fix: the shim never even looked at its own symbol table — it forwarded the request straight to ANGLE's eglGetProcAddress and returned whatever ANGLE answered. Zero interception on this road.

Why "usually" matters — the failure was silent

Nothing crashed at load time. The game just received a different function than KuDroid intended: a raw ANGLE function that knows nothing about Android display semantics. The symptoms show up later as a blank screen, a failed eglGetDisplay, or a wrong rendering backend — exactly the kind of bug that's hard to trace back to symbol resolution.

Same policy, both roads

After this commit, the two pipelines share the same policy: shim table first, ANGLE second, RTLD_DEFAULT last. Games that resolve everything through eglGetProcAddress (common with extension-heavy engines) and games that use plain dlsym now both receive bionic_eglGetDisplay.

05Why eglGetDisplay must be intercepted at all

The interception isn't cosmetic — bionic_eglGetDisplay performs three Android→iOS translations that ANGLE's real function knows nothing about.

1 · Kill the display argument

On Android, eglGetDisplay(display_id) accepts a real display pointer. On iOS there is no such display — ANGLE wants EGL_DEFAULT_DISPLAY (0).

The shim does (void)display_id; — the game's argument is discarded, and ANGLE always receives 0.

2 · Pick the right backend

ANGLE's real eglGetDisplay picks a default backend. The shim instead routes through eglGetPlatformDisplayEXT with an explicit attribute list that forces the Metal backend and Metal device type.

3 · Keep CAMetalLayer for surfaces only

The "window" (ANativeWindow → CAMetalLayer) belongs to eglCreateWindowSurface — never to the display. The shim enforces that separation: display = 0, layer = surface.

The backend fallback chain inside bionic_eglGetDisplay

EGL_PLATFORM_ANGLE_TYPE_METAL_ANGLE (0x3489) ← try first EGL_PLATFORM_ANGLE_TYPE_VULKAN_ANGLE (0x3450) ← if null EGL_PLATFORM_ANGLE_TYPE_DEFAULT_ANGLE (0x3204) ← if null real eglGetDisplay fallback ← if null return nullptr

All three attempts pass EGL_PLATFORM_ANGLE_ANGLE (0x3202) as the platform and native_display = 0, with the device type pinned to EGL_PLATFORM_ANGLE_DEVICE_TYPE_METAL_ANGLE (0x348A). Metal-first, because that's ANGLE's supported path on iOS.

What went wrong before the fix (in practice)
  • Real display pointer forwarded: a game that passes its own display value straight to ANGLE's real eglGetDisplay → invalid display on iOS → EGL_NO_DISPLAY or a crash.
  • Wrong backend chosen: ANGLE's default backend on the device may not be the Metal one the shim pins → no surfaces, black screen.
  • Silent symptom split: the dlsym road and the eglGetProcAddress road returned different functions for the same name — a Heisenbug that depended on which engine the game used.

Why the Vulkan entries were already "priority" but EGL display wasn't

The kShimPriority list existed before this commit, but it only covered surface translation: Vulkan's vkCreateAndroidSurfaceKHR and EGL's eglCreateWindowSurface — functions where receiving ANGLE/MoltenVK's real version would immediately break surface creation. eglGetDisplay was assumed to be harmless pass-through, so it lived only in the fallback table. This commit recognized that display creation is also semantic-laden on iOS (backend selection + display-id discard), so it promoted both display functions to priority status and mirrored the policy into eglGetProcAddress.

07Takeaways

💡 Interception is a resolution-time problem

A shim only works if the game is handed your function when it looks the symbol up. Every lookup API the game can use is a separate hole.

🔁 Two roads must agree

If dlsym returns the shim but eglGetProcAddress returns ANGLE's function, the same call behaves differently depending on the engine — the worst kind of bug.

🧭 Display ≠ window on iOS

Android's display object is meaningless under ANGLE/Metal; only the CAMetalLayer (a surface concept) is real. The shim is what enforces that.
